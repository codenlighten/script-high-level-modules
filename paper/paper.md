# Witness-Assisted Pairing Cryptography in Bitcoin Script

### BLS12-381 and Groth16 verification on a stack machine with a different cost model

**Status: preprint draft.** Every number in [tables.md](tables.md) is generated
from `results.json`, which is generated by measuring the code. Prose is written
by hand and can be wrong; the tables cannot silently describe a version of the
implementation that no longer exists.

---

## Abstract

We investigate whether modern pairing-based cryptography can be expressed
directly in Bitcoin Script, and what it costs when it is. We compile the
BLS12-381 field tower, G2 curve arithmetic, the Miller loop, the final
exponentiation, multi-pairing products and Groth16 verification into Bitcoin
locking predicates built from ordinary opcodes — `OP_MUL`, `OP_MOD`, `OP_ADD`,
`OP_PICK`, `OP_ROLL`, `OP_WITHIN` — with no pairing primitive, no extension-field
type, and no arithmetic opcode beyond arbitrary-precision integers.

Expensive intermediate values, principally field inversions, are supplied by the
spender and verified algebraically: `z = a⁻¹ (mod p)` becomes the constraint
`a·z ≡ 1 (mod p)`, with `z` bounded into `[0, p)` so that no second witness
encodes the same value.

**Both stages of a BLS12-381 pairing were deployed and spent on Bitcoin SV
mainnet**, as two transactions: the complete 63-round Miller loop as a
333,676-byte locking script, and the complete final exponentiation as a
474,207-byte one. That is 98.7% of a pairing by bytes.

The second was made possible by a 2/6 compressed representation of the
cyclotomic subgroup whose squaring is closed by construction, with a
decompression derived from f·f̄ = 1 as two linear equations over Fp2. It reduces
the final exponentiation from 592,008 to 473,466 bytes, across the default
500,000-byte script policy boundary.

What has not executed on chain is the *chaining*: a single script running the
loop and feeding its twelve outputs to the exponentiation is 817,031 bytes, past
the policy, and the 10,588 bytes by which the whole exceeds its two stages are
exactly that plumbing. It is validated against `bsv.Script.Interpreter`.

We construct a Groth16 verification predicate of 1,240,810 bytes and 774,756
opcodes that accepts a valid proof and rejects invalid proofs whose curve
membership and inversion witnesses remain valid, isolating failure to the
pairing equation itself. Multi-pairing compilation reduces size by sharing the
Miller accumulator, saving 609,794 bytes for two pairings and 1,223,178 for
three relative to independent evaluation.

Finally, we identify an **inverted cost model**: because a witnessed inversion
costs roughly four multiplications to verify rather than hundreds to compute,
affine coordinates outperform the projective coordinates that conventional
elliptic-curve implementation practice prescribes — and compressed cyclotomic
squaring, whose decompression costs an inversion and which is therefore normally
reserved for long squaring chains, becomes worth taking at once. Implementation
strategies optimal for processors are not necessarily optimal for
witness-assisted verification, and the same reversal appears in more than one
place.

## 1. Introduction

Bitcoin Script is usually described as a deliberately limited language for
expressing payment conditions. After the Genesis upgrade, Bitcoin SV's
interpreter admits arbitrary-precision integer arithmetic, and the question of
what can be *expressed* separates from the question of what is *conventional*.

This paper reports an empirical answer to a narrow version of that question:
how much of a bilinear pairing can be written as a Bitcoin locking script, and
what does it cost?

The contributions are:

1. **A compilation path** from BLS12-381 pairing arithmetic to Bitcoin Script
   primitives, through a typed, stack-tracking assembler with per-module
   pre- and post-conditions (§4–§6).
2. **A witness-assisted arithmetic model** in which the spender computes
   expensive values and the script verifies algebraic identities, with the
   canonicity obligation that makes this sound (§3).
3. **Empirical mainnet execution of both stages** of a pairing, as two
   transactions, with byte-exact reconstruction from source (§8). The final
   exponentiation reaches the network only because of the compression in §6.1.
4. **A multi-pairing result**: k pairings sharing one Miller accumulator, with
   measured savings (§7).
5. **A Groth16 verifier** and the precise separation between the values a
   spender may choose and the values the locking script fixes (§7.2).
5a. **Transaction-level decomposition**: a computation exceeding the script-size
   policy split across two inputs of one spend, bound by a shared output
   commitment, with both halves verified by the interpreter (§8.2).
6. **An inverted cost model** for elliptic-curve arithmetic under witness-
   assisted verification (§9).

We are explicit about what has *not* been shown. A complete pairing has not
executed on mainnet and cannot under current relay policy. The Groth16
construction verifies a statement fixed at locking time; a verifier accepting
public inputs at spend time requires on-chain scalar multiplication we price
but do not emit.

## 2. Background

### 2.1 The interpreter

Post-Genesis, script numbers are arbitrary precision up to 750,000 bytes and
`OP_MUL` and `OP_MOD` operate at 4,096 bits. Every property this work depends on
was measured rather than quoted, as passing probes.

Three behaviours shape everything below:

- **`OP_MOD` is truncated, not Euclidean.** `(−3) mod 5` is `−3`. A value that
  might be negative when it reaches `OP_MOD` must have the modulus added first,
  and this determines the schedule of nearly every module in §5.
- **`OP_NUM2BIN` writes a signed number**, so a high bit becomes a sign bit.
- **The stack is capped at 1000 elements**, which bounds the working set rather
  than the script.

### 2.2 BLS12-381 and the tower

BLS12-381 is a pairing-friendly curve with a 381-bit base field. The pairing
e : G₁ × G₂ → G_T satisfies e(aP, bQ) = e(P, Q)^{ab}, and is computed in two
stages: a **Miller loop** over the 63-bit curve parameter, then a **final
exponentiation** to (p¹² − 1)/r.

The field tower is
Fp2 = Fp[u]/(u² + 1), Fp6 = Fp2[v]/(v³ − ξ) with ξ = u + 1, and
Fp12 = Fp6[w]/(w² − v).

Because p ≡ 3 (mod 4), the Fp2 Frobenius is conjugation — a single negation —
which is why a degree-12 Frobenius costs seven multiplications rather than a
381-bit exponentiation (§5.4).

## 3. The witness-assisted model

### 3.1 The transformation

Computing a modular inverse in Script would require an extended Euclidean
algorithm or an exponentiation by p − 2. Instead the spender supplies `z` and
the script checks

```
a · z ≡ 1 (mod p)
```

which is one multiplication, one reduction and one comparison. In Fp2 it is one
Fp2 multiplication written out — four Fp multiplications and two comparisons.

Generally: **verification can be asymptotically and practically cheaper than
recomputation**, and a locking script is a verifier.

### 3.2 The obligation this creates

A witnessed value imposes two duties, and the second is where the bugs are.

**Soundness** — no *wrong* witness is accepted. `a · z ≡ 1` establishes this:
there is exactly one inverse.

**Canonicity** — no *second* witness is accepted either. Without a range check,
`z` and `z + p` both satisfy `a·z ≡ 1 (mod p)`, so a downstream comparison would
be comparing numbers that are congruent rather than equal. Every witnessed value
in this work is bounded into `[0, p)` by `OP_WITHIN`.

Four bugs of exactly this kind were found by systematic audit rather than by
testing, by asking of every module: *what can a spender choose, and is each
choice pinned to exactly one value?* Three were in code whose tests passed.

### 3.3 Testing witnesses adversarially

Every witnessed input is attacked on every run: near misses, off-by-p, sign
flips, zero, the modulus itself. The suite reports 1,279 forgery attempts, all
refused. This is separate from testing that correct inputs produce correct
outputs, and it catches a different class of defect.

## 4. The compilation path

```
high-level algorithm
      ↓  a JavaScript model — the specification, never the same code
field-operation schedule
      ↓  a typed, stack-tracking assembler
witness assignment
      ↓  hint(), replaying the algorithm to produce the spender's values
Bitcoin Script
      ↓  bsv.Script.Interpreter, under relay policy flags
accept / reject
```

Each module carries a `model` (what the answer is), an `emit` (how the script
computes it), `requires`/`ensures` contracts as intervals, and `cases`. The
model and the emitter are deliberately different code: a schedule and its
specification must be able to disagree, or the test is vacuous.

Contracts propagate. `fp2.mul` requires its inputs reduced into `[0, p)`; when
they are outputs of another module whose `ensures` said so, the requirement is
discharged and no check is emitted. When it is not discharged, a bound is
emitted. When it can be neither, the build fails. That third outcome is the
mechanism's purpose.

## 5. Field arithmetic

See **Table 1** for measured sizes.

### 5.1 Fp2 multiplication, and why the products stay unreduced

Karatsuba gives r₀ = t₀ − t₁ and r₁ = t₂ − t₀ − t₁ from three products. Leaving
t₀ and t₁ *unreduced* makes the imaginary part identically a₀b₁ + a₁b₀ — a sum
of two non-negative numbers — so it needs no correction before a truncated
`OP_MOD`. Only the real part is a genuine difference and pays for one reduction
and one addition of p. Reducing t₀ and t₁ up front instead costs two extra
`OP_MOD`s *and* still needs a 2p correction, because the reduced difference no
longer carries the identity that makes it positive.

### 5.2 Cyclotomic squaring, and the basis that hid

After the easy part of the final exponentiation the accumulator lies in
G_Φ6(Fp2), where Granger–Scott squaring is available. Two implementations
written from the nested Fp6[w] indexing disagreed with general squaring and were
discarded.

The third works because of a change of *presentation*, not of algebra:
w² = v and w⁶ = ξ mean Fp12 is equally Fp2[w]/(w⁶ − ξ) with basis 1, w, …, w⁵,
and since (w³)² = ξ, the element is three Fp4 coefficients — **(g₀,g₃), (g₁,g₄),
(g₂,g₅)**. Those pairs are what the nested indexing conceals, and both failures
had them wrong.

### 5.3 Sparse line multiplication

Nine of a Miller line's twelve Fp2 coefficients are zero. On a processor the
zeros are skipped at negligible cost; in a locking script a multiplication is
*bytes*, present whether or not it does anything. Writing the product against
the three live coefficients takes it from eighteen Fp2 multiplications to
fourteen.

### 5.4 Frobenius

f ↦ f^p is six conjugations and seven multiplications by derived constants. The
module's *model* is the literal exponentiation f^p, so what is proven is that the
shortcut equals the thing it is a shortcut for, rather than equalling another
copy of itself.

## 6. The Miller loop

The loop over |x| = 0xd201000000010000 performs 63 squarings, 63 tangent steps,
5 chord steps and 68 line products. Two implementation points matter.

**The squaring belongs to the bit, not to the line.** A set bit contributes two
lines and still one square. Squaring before the chord yields f² where f was
wanted — a wrong answer costing 2,301 extra bytes to reach, which every
component test tolerated.

**λ is computed once.** The obvious factoring derives the line from the slope
and then asks a general point-addition routine for the next point, which
recomputes the slope: a second inversion for a number already in hand. Deriving
the next point from λ directly gives **68 inversions rather than 136**, halving
the witness.

### 6.1 Compressed squaring, and a second inverted trade

Read the Granger–Scott identities in the Fp4 basis — f = c₀ + c₁w + c₂w² over
Fp4 = Fp2[s]/(s² − ξ) with s = w³ — and c₁′ and c₂′ depend only on c₁ and c₂.
So {c₁, c₂} is closed under squaring, c₀ can be dropped, and squaring costs two
Fp4 squarings instead of three. That is a 2/6 compression obtained by *reading*
formulas already verified rather than by deriving new ones.

Compression is only useful if one can come back, and decompression is where the
technique normally stops paying: it costs a field inversion, so it is reserved
for long runs of squarings. Under witness-assisted verification the inversion is
four multiplications, and the break-even moves down far enough that it is worth
taking immediately.

The recovery is derived rather than recalled. For f in the cyclotomic subgroup
f·f̄ = 1, and with f̄ = c̄₀ − c̄₁w + c̄₂w² two of the three resulting Fp4 equations
are **linear** in c₀ = x + ys:

```
w²:  2(c₀c̄₂)₀ = N(c₁)      ⟹   c₂ᵣ·x − ξc₂ₛ·y  =  N(c₁)/2
w¹:  2(c₁c̄₀)₁ = −N(c₂)     ⟹   c₁ₛ·x −   c₁ᵣ·y  = −N(c₂)/2
```

writing u = uᵣ + uₛs and N(u) = uᵣ² − ξuₛ². A 2×2 solve over Fp2, one witnessed
inversion of the determinant, and both equations scaled by two so nothing is
halved.

| | bytes |
| --- | ---: |
| `fp12.powX`, uncompressed ladder | 98,902 |
| `fp12.powXc`, compressed | 73,674 |
| final exponentiation, before | 592,008 |
| final exponentiation, after | **473,466** |
| e(P, Q), before | 935,334 |
| e(P, Q), after | 817,031 |

25.5% off a ladder, 20.0% off the final exponentiation, 12.6% off a pairing —
and the exponentiation crosses the 500,000-byte policy boundary — which is why
it is on mainnet and not only in the interpreter.

The determinant ξ·c₁ₛc₂ₛ − c₁ᵣc₂ᵣ can vanish, and then nothing is recovered.
That is a **completeness** limit, not a soundness one: it cannot make a wrong
pairing verify, only a right one fail, and the values it depends on are
determined by the computation rather than chosen by the spender.

`fp12.powXc` is checked against the literal f^|x| by general exponentiation —
the same model `fp12.powX` carries — so the compressed schedule is verified
against a specification no part of it produced.

## 7. Products of pairings, and Groth16

### 7.1 Sharing the accumulator

Because the squaring belongs to the bit, k pairings evaluated on one accumulator
pay for 63 squarings between them and **one** final exponentiation. See
**Table 3**: each pairing after the first costs about 204,000 bytes rather than
935,000.

### 7.2 Binding the verification key to the predicate

Groth16 verification is

```
e(A, B) · e(−L, γ) · e(−C, δ) = e(α, β)
```

with L = IC₀ + Σ xᵢ·ICᵢ. **The soundness is not the arithmetic; it is who
chooses what.** Only A, B and C come from the unlocking script. γ, δ and L are
pushed as constants by the locking script, and e(α, β) is the constant they are
compared against.

A predicate taking all three pairs as inputs is a check of the *equation* and
not a verifier: a spender free to choose γ can choose one satisfying the equation
for a proof of nothing. The two constructions differ by 490 bytes of pushed
constant, and the test suite asserts the separation on every run.

### 7.3 The statement is the UTXO

L is a constant because the statement is fixed when the coin is locked. A
covenant that pays out to whoever proves *this* knows its public inputs when it
is written, so L is computed off chain once and pushed as 96 bytes rather than
costing about 40,000 bytes of on-chain scalar multiplication per input.

This is a structural fit rather than an optimisation. In a general verifier the
statement arrives with the proof; in a UTXO the statement *is* the output. A
verifier accepting public inputs at spend time is a different object and does
need the multiplications.

### 7.4 Fault-isolation testing

The negative cases are constructed so that failure can only be attributed to the
pairing equation. For an A and a C each displaced by one generator:

```
CurveValid = 1 ∧ WitnessValid = 1 ∧ FieldArithmeticValid = 1
                ∧ Groth16Equation = 0   ⟹  Script = FALSE
```

Every point remains on the curve; every witnessed inverse remains correct for
the points supplied, because the witness generator recomputes them. Nothing
fails until the equation does. A verifier that rejects invalid proofs because
they are malformed has not been shown to check the intended relation.

## 8. The mainnet experiment

See **Table 5** and **Table 7**.

The complete Miller loop was deployed as a 333,676-byte locking script and
spent. One `f ↦ f^|x|` ladder was deployed as 99,631 bytes and spent. Each deployed script is rebuilt from source and compared byte for byte against
the chain; 15 of 15 reconstruct exactly.

**Scope.** 98.7% of one pairing by bytes has executed on the network, in two
transactions: the Miller-loop stage complete, and the final exponentiation
complete. Neither figure includes the deployed `fp12.powX`, a correct
uncompressed ladder the network also executed and which §6.1 has since taken off
the critical path; counting a superseded version would inflate the number.

What remains is the 10,588 bytes of chaining between the stages. A pairing in
one script is 817,031 bytes and past the policy, so the composition itself has
run only in the interpreter. "Both stages have executed on mainnet" is the
claim; "a pairing has executed on mainnet" is not.

### 8.1 Systems findings

Scripts of this size exposed two wallet defects that had never mattered at a few
hundred bytes.

**Coin selection inherits ancestry.** Outputs were taken in indexer order, which
swept up dust from earlier deployments — and that dust sits at the *end* of the
unconfirmed chain those deployments created. A single fresh 50,000-satoshi
output funds a 334 KB transaction alone; funded by three satoshis of dust first,
the same transaction inherited fourteen links of ancestry and was rejected with
`too-long-mempool-chain`. The fee was never the problem.

**Fee estimation must be script-derived.** Funding stopped at a fixed
`amount + 5000` constant — reasonable for a 400-byte covenant, meaningless for a
script whose fee alone is 33,389 satoshis. It did not underfund; it swept the
wallet, which is how the first defect acquired its dust.

Both are ordinary bugs. We report them because they are the kind of assumption
that only very large scripts falsify, and anyone repeating this work will meet
them.

## 8.2 Decomposing across a transaction

A pairing in one script is 817,031 bytes against a 500,000-byte policy, and the
gap is not closable by optimisation. It is closable by putting the composition
somewhere other than the script.

```
input 0   the Miller loop            publishes f as an OP_RETURN output
input 1   the final exponentiation   consumes that same output
```

Both inputs of a spend observe the same `hashOutputs`. If each requires that
commitment to be the data output *it* constructs, the two must have constructed
identical bytes, so input 1's f is input 0's f — enforced by the transaction
rather than assumed. Neither script contains the other's code, which is the
necessary property: a covenant can only commit to a successor whose bytes it can
build, and a 344 KB script cannot carry a 475 KB one.

| | lock | unlock | verdict |
| --- | ---: | ---: | --- |
| input 0, `pairing.publish` | 343,799 | 350,922 | accepted |
| input 1, `pairing.consume` | 475,017 | 479,302 | accepted |
| output, `OP_RETURN` | 588 | — | twelve Fp12 coefficients |

Both inputs are verified by `bsv.Script.Interpreter` under relay policy flags.
What the network establishes, in one transaction, is that the Miller loop ran
correctly on P and Q, that its twelve outputs were published, that the same
twelve were consumed, and that their final exponentiation is e(P, Q).

**Joint grinding.** OP_PUSH_TX requires each preimage to satisfy a canonical
low-S condition, ordinarily obtained by grinding that input's `nSequence`. But
`hashSequence` commits to *every* input's sequence, so grinding input 0
invalidates input 1's preimage and conversely: independent grinds do not
compose. The search is over the pair. About one preimage in fifty passes, so a
pair lands in a few thousand attempts — 733 in the reported run. Rebuilding a
preimage carrying a 344 KB `scriptCode` that many times is unnecessary: only 36
bytes change, so each preimage is constructed once and `hashSequence` and
`nSequence` are patched in place, then checked against the ones the library
produces.

**A constraint this surfaces.** OP_PUSH_TX's preimage *contains the script it
unlocks*, so a covenant's unlocking script is as large as its locking script.
`pairing.consume` locks in 475,017 bytes and unlocks in 479,302 — 20,698 under
the policy. For covenants of this size the binding limit is the **unlocking**
script, not the locking one, which is not where one would look for it.

This generalises past pairings. Any computation too large for one script can be
cut at a point where the intermediate state is small, with each piece requiring
the same commitment to that state. The state here is 588 bytes for a computation
of 817,031, and the cut is where the two stages of the pairing already meet.

## 9. An inverted cost model

Conventional elliptic-curve implementation assumes I ≫ M and chooses projective
or Jacobian coordinates to eliminate inversions, accepting several extra
multiplications per step.

Under witness-assisted verification, an Fp2 inversion is one Fp2 multiplication
and two range checks. Empirically I_witnessed ≈ 4M, so the trade reverses:

> **affine > projective**

The Miller loop here is affine throughout, and projective formulas would make it
larger. We state this as the paper's most transferable claim:

> The optimal cryptographic algorithm depends on the verifier's computational
> model. A witness-assisted stack machine has a different cost hierarchy from a
> processor, and received implementation wisdom does not transfer unexamined.

Three further consequences of the same principle appear above. Multiplying by
zero is free on a processor and costs bytes in a script (§5.3). An LSB-first
ladder's multiplication-by-one is free at runtime and costs 3,110 bytes when
unrolled — the marginal cost of an Fp12 product inside a composition (§5,
Table 1). And compressed cyclotomic squaring, whose decompression
inversion normally confines it to long squaring chains, pays immediately here
(§6.1) — the same reversal, arrived at independently.

## 9.1 Instruction selection: letting the target decide

Stating "affine beats projective in Script" is a finding about one construction.
Making it *operational* is a different thing, and the repository does: given
several modules that compute the same mathematical function, `select()` proves
they agree and then chooses by a stated objective over the cost vector
(locking bytes, unlocking bytes, total, opcodes, peak stack depth, fee).

```
f ↦ f² in Fp12            lock     unlock      total   opcodes  stack
  fp12.sqr               2,292        588      2,880     1,540     37
  fp12.cycSqr            1,259        588      1,847       968     34  ◀

f ↦ f^|x| in Fp12
  fp12.powX             98,902        588     99,490    71,954     61
  fp12.powXc            73,582      1,175     74,757    54,204     71  ◀
```

Nothing there was told that the cyclotomic identities or the compression win.
Both were emitted and counted. This is the smallest honest form of an
instruction-selection pass over mathematics: the same function, several
lowerings, and a target-specific cost model choosing among them — which is what
turns §9's observation from an assertion into a mechanism.

The `total` column is where a witnessed construction can lose. `fp12.powXc`
buys 25,320 bytes of locking script for 587 bytes of unlocking script; a
construction with a worse ratio would be rejected on the same evidence, and the
objective is a flag rather than an assumption.

**The agreement step is the contribution, not the ranking.** A selector that
picks the cheaper of two implementations without first establishing that they
compute the same thing is a benchmark attached to a bug. And comparing their
*models* is insufficient — we found this by trying it. `fp12.cycSqr`'s model is
the general square, correct on all of Fp12; only its emitted script is confined
to the cyclotomic subgroup. Two candidates whose models agree can have scripts
that do not. The check therefore verifies each candidate's script against its
own model on every vector, and the models against each other:

```
script_i = model_i = model_j = script_j
```

Run off the subgroup the same two candidates are refused rather than ranked, and
that refusal is itself a test case. Agreement is always agreement *on a domain*,
and each contest records the one its vectors came from; "cheaper" without "and
equivalent, here" is not a result.

## 10. Correctness methodology

1. **Independent reference.** The BigInt implementation agrees with
   `@noble/curves` on all twelve Fp12 coefficients — not merely on bilinearity,
   which a wrong pairing can also satisfy. An early line function here was
   non-degenerate, produced order-r values, passed every component test, and was
   wrong; byte equality caught it. Eight chosen scalar pairs, three boundary
   pairs (1 and r−1 in each position), and twelve generated from a printed seed:
   320 assertions in all.
2. **Model versus emitter.** Each module's specification is different code from
   its schedule.
3. **The real interpreter**, under relay policy flags.
4. **Adversarial witnesses**, on every run: 1,279 forged witnesses refused.
5. **Published vectors** where they exist (RFC 6238, BIP-340), and the host
   library's own secp256k1 and Merkle implementations.
6. **Randomised differential testing of every module** against its own model,
   on inputs generated from the module's stated domain rather than chosen: 44
   modules, none disagreeing. The two modules whose domain is a *subgroup* —
   which an interval cannot state — carry a generator that runs an easy part to
   produce one, so those rounds test the module where it is defined rather than
   reporting a disagreement that is the module telling the truth.
7. **Boundary values**: 0, 1, p − 1, and both coefficients at p − 1.
8. **Byte-exact chain reconstruction** of every deployed script.
9. **Generated figures.** Every number in Table 1–7 is produced by measurement.

### 10.1 Reproducibility of the numbers, not only of the artifact

Three documents in this repository quoted measured figures in prose and all
three had drifted — one claimed an RSA verifier was 955 bytes when it was 969,
another that a curve addition was 139 bytes when a soundness fix had made it 167.

Measurements are therefore generated:

```
source → measurement → results.json → tables → this paper
```

rather than `source → someone remembers → a number in a PDF`. The test suite
fails if `results.json` disagrees with the code, and if `tables.md` disagrees
with `results.json`.

## 11. Limitations

- **A complete pairing has not executed on mainnet** in a single script and
  cannot at 817,031 bytes under a 500,000-byte script policy. Both of its stages
  have, separately; the 10,588 bytes that chain them have run only in the
  interpreter.
- **`fp12.powX` is deployed but superseded.** It computes a correct f^|x| and
  the network executed it; `fp12.powXc` replaced it, so it is not a component of
  the pairing measured here and its bytes are not counted as such.
- **The Groth16 verifier is for a fixed statement.** Spend-time public inputs
  need on-chain scalar multiplication, priced at about 40,000 bytes per input
  but not emitted.
- **The Groth16 fixture is constructed from the group law, not from a circuit.**
  It establishes that the verifier checks the intended relation; Groth16's own
  soundness is out of scope.
- **`fp12.cycSqr` is correct only on the cyclotomic subgroup**, a precondition
  the interval-based contract system cannot express. It is discharged
  structurally by the easy part, and stated as a note rather than enforced.
- **Policy, not consensus.** The 500,000-byte boundary is a relay-policy number.
- **One implementation of the compiler.** The measurements are of this emitter;
  a better one would produce smaller scripts.

## 12. Roadmap

The final exponentiation is 57.9% of a pairing and is still where remaining
effort belongs, though §6.1 has taken it below the policy boundary. Better
addition chains, further witness-assisted subcomputations and transaction-level
decomposition across several outputs are all open. Whether a whole pairing can
be brought under the boundary in one script is an engineering question, not an
expressiveness one. Bringing the chaining under the boundary — which is a
further 344,000 bytes off the two stages together — is what would turn "both
stages have executed" into "a pairing has executed".

Beyond BLS12-381: BLS signature verification is a two-pairing product; KZG
opening is likewise. Both land directly on the multi-pairing predicate in §7.1.

Further out, §9.1 is the seed of something larger. If a target-specific cost
model can choose between two lowerings of a squaring, it can choose between
lowerings of anything, and the interesting object stops being any particular
pairing implementation and becomes the compiler: a mathematical predicate in,
a locking script out, with the choice of representation, the placement of
witnesses and the stack schedule all decided by measurement against this target
rather than inherited from a processor's. The results here suggest that such a
compiler would make materially different choices from a conventional one, and
that those choices are discoverable rather than needing to be known in advance.

## 13. Conclusion

Bitcoin Script has no pairing opcode, no extension-field type, and no inversion
primitive. It has arbitrary-precision multiplication and modular reduction, and
that turns out to be sufficient to express a BLS12-381 pairing and a Groth16
verifier — at a price that is now measured rather than argued about, with the
Miller-loop stage executed by the network.

The general lesson is not about pairings. It is that shifting computation into
prover-supplied witnesses, and verifying algebraic identities instead of
recomputing values, changes which algorithm is optimal. The absence of an opcode
is not the absence of the computation; it is a cost, and costs can be measured.

## Artifact

Source, generator, test vectors, deployed scripts, transaction identifiers and
a one-command reproduction path accompany this paper.

```
npm test                # everything, including one whole pairing in the interpreter
npm run pairing:prove   # emit e(P, Q), run it, check twelve coefficients
npm run groth16         # emit the verifier: one valid proof, two forged
npm run paper           # regenerate results.json and tables.md from the code
npm run verify:chain    # rebuild every deployed script and compare to the chain
```
